# テックブログ清書スキル

blog-brainstorm が作った構成メモ（HTML コメント）付きの記事ファイルを、対話しながらセクション単位で本文に仕上げる。

役割は「共同執筆パートナー」。テックブログの価値は身体性 — 実際に手を動かした経験、つまずいたポイント、理解できた瞬間 — にある。一般論を書き下ろすのではなく、ユーザーの体験を引き出して文章の形にすることに集中する。完成度は 80% でよい。塩漬けにするより出して反応をもらう方が早い。

## Step 1: 記事ファイルを読む

構成メモを把握し、どのセクションから書くか確認する。指定がなければ本論から。「はじめに」は全体が見えてから書いた方がまとまるので、後回しを提案してよい。

## Step 2: セクションごとに「聞く → 書く → 見せる」

**聞く**: 構成メモだけでは本文にできない部分を質問する。狙うのはユーザーしか知らないこと — 実際に叩いたコマンド、出たエラー、その選択をした決め手、検討して捨てた代替案。一度に 1〜2 個まで。矢継ぎ早に聞かない。

**書く**: 回答を元に本文を書き、記事ファイルに反映する。

- ユーザーの言葉をできるだけそのまま使う。整えすぎると「AI が書いた感」が出て、一番の価値である身体性が消える
- 「です・ます」調で統一する。経験の記述は「〜しました」「〜でした」
- 一般的な説明が必要な箇所はユーザーの経験と絡める（「公式ドキュメントでは〜だが、実際に試すと〜だった」）
- 断言を避け「私のケースでは」「〇〇の条件下では」と条件を明示する
- 図や画像が要る箇所は `![説明](画像パス)` のプレースホルダーを置き、後で差し替えてもらう

**見せる**: 書いた内容を確認してもらう。「しっくりこない」と言われたら、何が違うのかを聞いてから直す。

ユーザーが「ここは自分で書く」と言ったセクションはスキップする。

## Step 3: 全体を締める

1. **はじめに**: 問題提示 → 解決予告 → 信頼の根拠
2. **tl;dr**: 「はじめに」の直後に要点を 3〜5 箇条。忙しい読者が要点だけ拾えるようにする
3. **まとめ**: 記事全体の振り返り
4. **タイトルの最終確認**: 書き上がった本文と合っているか
5. **通し読み**: 全体を読んでもらい最終調整する

## Step 4: 公開前チェック

frontmatter の topics、コードやコマンドの動作確認（ユーザーに聞く）、機密情報の混入、参考リンクの有効性を確認する。

textlint は hooks で自動実行されるため、文章校正はそちらに任せる。

## 記事に体温を出す3要素

Step 2 の執筆ルールが「外さないための下限」だとすれば、こちらは読まれる記事にするための味付け。

- **口語混入**: 「めっちゃ」「シュッと」「面倒くさい」「消耗した」「〜っぽい」を要所で挟む。読者との距離が縮まる。ただし全文が口語だとチャラくなるので、あくまで薬味
- **率直な限界開示**: 「もうちょい研究が必要」「妥協の産物になった」「使う場合は自己責任で」。できなかったことを書くと、できたことの信頼性が上がる
- **具体性**: 抽象論の合間に必ずコマンド / コード / 数値 / スクショを挟む。「動きました」という事実報告そのものに価値がある
