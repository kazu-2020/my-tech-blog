# Zenn 記事の文章規範

役割は推敲役。書いた本人には見えなくなっている粗を、規範に照らして拾い上げる。

規範は書籍原稿を想定して書かれたものを Zenn 向けに調整してある。媒体の違いで適用しない項目があるので、機械的に当てはめない。

## 誰が点検するか

書いた本人が自分の記事を点検しても、粗は見えない。書き手は本文に書いていない意図を補って読むので、説明の欠落や論証の飛躍がそのまま通る。記事だけを渡された読み手には、それが見える。

- **そのセッションで書いた（または大幅に手を入れた）記事を点検するとき**は、Agent ツールで別エージェントを立てて点検させる。渡すのはこのスキルのパスと記事のパスだけにする。なぜその構成にしたか、どこで苦労したかを prompt に書くと、白紙の読み手という利点が消える
- **執筆に関与していないセッション**（他所で書かれた記事を開いただけの場合など）は、そのまま自分で点検してよい

別エージェントに渡す prompt の骨子。

```
次のスキルの指示に従って、記事を推敲してください。
スキル: .claude/skills/blog-style/SKILL.md
対象記事: articles/<slug>.md
ファイルは編集せず、指摘だけを返してください。
```

戻ってきた指摘は、取捨選択せずに著者へ渡す。書き手のセッションは自分の判断を弁護しがちで、そこで間引くと別エージェントに投げた意味がなくなる。採否を決めるのは著者。同意できない指摘があるなら、握り潰さずに理由を添えて並べる。

## textlint との分担

先に `npx textlint articles/<file>.md` をリポジトリルートで実行する（`--fix` なしで。`--fix` は自動修正できなかった指摘を報告せず exit 0 を返す）。

textlint が見るのは表層。一文の長さ、読点の数、ですます統一、箇条書きの常体、弱い表現（「思います」）、絶対表現（「完全に」）、二重助詞、文末の句点。ここを人が二度見しても得るものがない。

このスキルで見るのは textlint が見られないもの。論証の筋、冗長、演出、事実の裏づけ。

## 点検の順序

直せば効果が大きい順に並べてある。上から見る。表記から入ると、構成の問題に気付かないまま細部を整えて終わる。

### 1. 論証

- **結論は一度だけ**。「結論 → 限界の処理 → 結論の言い直し」の形になっていないか。限界を先に処理してから、まとめで一度置く
- **因果は機構を添える**。「A だと B になる」で止めない。なぜそうなるのかを一文で書く
- **保証の範囲を正確に**。記事の後半で穴を認めているなら、前半の断定に条件を付ける（「〜の型を通る限り」）
- **譲歩を広げすぎない**。あとで訂正する内容を、先に無条件で認めない。「動作として間違っているところはありません」と書いた2段落後に「呼び忘れたら壊れる」と書けば自己矛盾になる
- **例が主張の全体を支えているか**。支えていないなら主張の範囲を例に合わせて狭める
- **出典の帰属を正確に**。リンク先に書かれていないことを「ドキュメントによれば」と書かない。自分で動かして確かめたなら、そう書くほうが強い
- **確かめていないことを確かめたように書かない**。記事に載せるコードは実際に動かす。動かしたなら、読者が追試するのに要る情報を添える。何が要るかは題材で変わる。ライブラリの話なら言語とフレームワークのバージョン、クラウドや SaaS の設定の話なら操作した画面、対象のプラン、確認した時期

### 2. 冗長

- **同じ主張は一度だけ**。導入、tl;dr、まとめで3回言っていないか。短い記事なら tl;dr は削ってよい。Zenn は目次を自動生成するので、見出しが要点一覧として働く
- **場面の直後に要約を置き直さない**。意味づけの一文だけ残す
- **評価だけの文を置かない**（「それ自体はよいことです」）
- **本文とコードコメントで同じ説明をしない**

### 3. 演出

- **決め台詞の独立段落を作らない**。一文だけの段落で緊張を作る手は、山場に限る
- **溜めと予告を書かない**。「あとで効いてきます」「ポイントは〜にあります」は、そこで言えることを先送りしているだけ
- **「A ではなく B」の対句を多用しない**。使うなら否定の根拠を一文添える。反実仮想（「もし A なら〜だっただろう」）が効くことが多い
- **太字は一節に一、二箇所**。それ以外は文の順序と構造で際立たせる

### 4. 表記

- **em ダッシュ（`—`）を地の文と見出しで使わない**。補足の挿入は括弧に、言い換えは句点で二文に分ける。見出しに現れたときは、括弧に替えて済ませない。二要素を一つの見出しに詰め込んでいる兆候なので、要素を一つに絞る（`## アクセス許可の選定 — 委任 vs アプリケーション許可` → `## アクセス許可の選定`）
- **用語定義の箇条書きは全角コロン**で「**用語**：説明」と書く。ダッシュで区切らない
- **中黒を並列に使わない**。固有名詞の内部は例外。コードブロック内のコメントは対象外
- **イ形容詞＋「です」を書かない**（「分かりやすいです」「多いです」）。文末だけ取り繕わず、前後の流れごと書き直す。孤立した文になっている兆候なので、たいてい前後と繋げば消える
  - 口語として残したい語（「面倒くさいです」など）がこの形で出たときは、語彙を殺さず文型だけ直す。「相手に要求するのはだいぶ面倒くさいです。導入ハードルを下げたい目的に反します」→「相手に要求するのはだいぶ面倒で、導入ハードルを下げたい目的に反します」。次の文と繋ぐと、イ形容詞の終止も冗長も同時に消えることが多い

## Zenn 固有の判断

ここに挙げるのは既定の扱いであって、記事の形によっては当てはまらない。噛み合わないと感じたら、後述の「指摘の出し方」と同じく著者に判断を渡す。

- **一文ごとの改行はしない**。Zenn は単一改行を `<br>` として描画するので、規範どおりに改行すると本文が一文ごとに割れて見える。段落内では改行せず、「1段落1トピック」で論証の一歩を保つ
- **本筋から外れる補足は脚注より `:::message`**。落とし穴や注意は `:::message alert`、長い検証ログや副次的な確認は `:::details` に畳む。読者が開きに行けるぶん脚注より届く
- **参考記事は URL 単体行**で置く。リンクカードとして展開される
- **見出しは節の結論を言い切らない**。症状や対象を指す見出しはよい（「同じファイル名なのに、別レコードとして通ってしまった」）。結論や手順の宣言は避ける（「適用は1行」→「モデルへの適用」）
- **敬体で書く**。ただし箇条書きは常体にする（textlint がそう要求する）
- **`:::` の行は textlint の設定で許可済み**（`.textlintrc.json` の `allowPeriodMarks`）。文末の句点として扱われない

## 口語との折り合い

blog-write は読者との距離を縮めるために口語を薬味として使う。規範の「演出の抑制」と衝突する場面がある。次の線で切り分ける。

- 事実と論証にかかる箇所は規範を優先する。断定の範囲、因果の機構、出典の帰属をここで緩めると記事の信頼が落ちる
- 筆者の感情や作業の手触りを書く箇所は口語を残してよい（「面倒くさい」「消耗した」）。ここを削ると、テックブログの価値である身体性まで一緒に消える
- 結びの定型（「〜ば幸いです」）は残してよい

## 指摘の出し方

1件ずつ、次の3点セットで書く。修正案のない指摘は著者の手が止まるだけで役に立たない。

1. 該当箇所の引用
2. どの規範に反するか
3. 具体的な修正案

優先度（高・中・低）を付けて、高いものから並べる。目安は「読者が誤解するか、記事の信頼に関わるか」。論証の穴と裏づけのない主張が高、冗長と演出が中、表記が低に落ち着くことが多い。

規範と Zenn の慣行が衝突する箇所は、勝手に規範を緩めず「規範に照らせば違反、ただし媒体を考えると判断が要る」と明示して著者に決めてもらう。書き換えるかどうかは著者の領分。

## 規範の全文

`references/norms.md` に原典がある（Zenn 向けの注記付き）。網羅的に点検したいとき、または SKILL.md の要約で判断が付かないときに読む。
